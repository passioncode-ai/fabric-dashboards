## Request (operator, 2026-09-28, translated)

Systematize the local agents that each have their own dashboard. Describe how agents are created: the communication
protocol between agents (MCP, CLI), how authorization works, where settings and files
live so they survive reinstalls, caching. Describe how a local dashboard is built so it
is always alive, comes back after a restart, always answers and never multiplies —
derived from studying every local dashboard we have. Ship one skill set for the whole
Fabric family. Build **Fabric Dashboards**: an app that finds every dashboard speaking
the protocol, lets the operator switch each on/off, restart it and see everything, with
a screen of the latest updates across agents, notifications, and dashboards opened
inside the app instead of browser tabs.

Grill answers (same day):

- Homes: protocol in `fabric-agent-contract`, skills in the `fabric-agent-adapter`
  plugin, app in new `passioncode-ai/fabric-dashboards`.
- Stack: "the way our products are built now, brand respected, like the mail app" →
  Fabric Inbox's Electron shell and brand pipeline.
- Scope: every local agent service on the operator's Mac; study each, derive the common
  protocol; services start, update, restart, report, notify; an activity screen across
  agents.
- Release: full release into the `passioncode-ai` org; check every PassionCode.ai skill
  is released; review the skill architecture across projects incl. Project
  Observatory; consider one self-updating npm package that installs everything for
  every agent.
